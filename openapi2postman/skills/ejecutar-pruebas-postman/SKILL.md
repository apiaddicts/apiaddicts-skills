# Run Postman contract tests (Newman / Postman CLI)

This skill runs a `.postman_collection.json` collection with its `.postman_environment.json` environment, leaves the report where the user asks and summarizes the result. Verified with **Newman 6** and **Postman CLI 1.62.0** on collections generated by openapi2postman 2.4.3.

Follow the steps in order. **Don't run anything against an API until the user has confirmed collection, environment and host** (step 1).

## Step 1: identify what is going to run

1. Ask for or locate the **collection** and the **environment**. If they come from openapi2postman, they are in the config's `target_folder`.
2. Read the environment and show the user the `host` (+ `port` + `basePath`) it will run against. Ask for confirmation.
3. **Review the environment before running** and warn if you find any of these (don't fill them in yourself):
   - Empty `host`: every request will fail.
   - Empty tokens: the variable named after the security scheme, `not_authorized_token`, `forbidden_token`. Without them, cases with auth fail.
   - openapi2postman filler values (`anystring`, `anydate`, `badstring`): the real backend may reject them in the 2xx cases.
   - The `Get OAuth2 Token` request with username and password `cambiame`.
4. **Real environments with writes**: if the collection has POST/PUT/PATCH/DELETE (it was generated without `read_only: true`) and the host is not local/development, warn that it **will create, modify or delete data** and ask for explicit confirmation.

## Step 2: choose the tool

Present both options and ask which one to use:

| | **Newman** | **Postman CLI** |
|---|---|---|
| What it is | Postman's open source runner (Apache-2.0), npm package `newman` | Postman's official CLI, proprietary binary (npm `postman-cli`) |
| Size | Small | ~292 MB (npm downloads the platform binary: Windows x64, macOS x64/arm64, Linux x64/arm64) |
| Login | Never | Not needed for local files. Shows `No authorization data found...` but runs anyway |
| Telemetry | No | **Sends analytics by default**: always use `--no-report-events`. It also stores an `installationId` in `~/.postman/postmanrc` and checks for updates |
| Included reports | cli, json, junit. HTML with the extra reporter `newman-reporter-htmlextra` | cli, json, junit, html |
| Recommended for | CI/pipelines, environments without a Postman account | Teams already using Postman Cloud |

Both require Node.js + npm to be installed via npm (`node -v`, `npm -v`).

## Step 3: check whether it is installed

```bash
newman --version      # Newman
postman --version     # Postman CLI
```

- If it returns a version, the tool is installed. For Postman CLI, also confirm it is the CLI and not something else in the PATH: `postman collection run --help` must list options such as `--reporter-json-structure`.
- If it fails with "command not found" or "is not recognized", **it is not installed**. Go to step 4.

## Step 4: if it is not installed, ask permission

**Never install without permission.** Offer both modes and wait for the answer:

| Mode | Newman | Postman CLI | What it leaves on the machine |
|---|---|---|---|
| **Global** | `npm install -g newman` (+ `npm install -g newman-reporter-htmlextra` if they want HTML) | `npm install -g postman-cli` | Stays installed and in the PATH. Removed with `npm uninstall -g <package>` |
| **Temporary** (this run only) | `npx -y -p newman@6 newman run ...` (+ `-p newman-reporter-htmlextra` if they want HTML) | `npx -y -p postman-cli postman collection run ...` | Nothing in the PATH. Only stays in the npm cache (`npm cache clean --force` to clear it). The first time it takes a while to download (Postman CLI ~30 s) |

Notes:
- The "classic" HTML reporter `newman-reporter-html` **is not compatible with Newman 6** (npm fails with `ERESOLVE`). Use `newman-reporter-htmlextra`.
- If the user chooses global and `npm install -g` fails due to permissions (`EACCES` on Linux/Mac), don't use `sudo`: suggest the temporary mode.

## Step 5: ask for report format and output folder

Ask both things, without assuming:

1. **Format(s)**, they can be combined:
   - `cli`: console output (always included, to see progress).
   - `json`: machine-readable report.
   - `junit`: XML for CI (Jenkins, GitLab, Azure DevOps). One `testsuite` per case and one `testcase` per assertion.
   - `html`: browsable report (Newman: `htmlextra`; Postman CLI: built-in `html`).
2. **Output folder**, e.g. `./reports`. Both tools create the folder if it does not exist.

The step 7 summary needs a JSON with Newman structure. **If the user did not ask for `json`, generate it anyway** in the same folder (`summary.json`) and tell them. If they prefer not to keep it, delete it at the end.

## Step 6: run

Variables used below: `COL` = collection, `ENV` = environment, `OUT` = output folder.

### Newman

```bash
newman run "$COL" -e "$ENV" \
  -r cli,json,junit,htmlextra \
  --reporter-json-export "$OUT/results.json" \
  --reporter-junit-export "$OUT/results.xml" \
  --reporter-htmlextra-export "$OUT/results.html"
```
Include in `-r` and in the `--reporter-*-export` options **only** the chosen formats (+ json). In temporary mode, replace `newman` with `npx -y -p newman@6 -p newman-reporter-htmlextra newman` (the `-p newman-reporter-htmlextra` only if HTML was requested).

### Postman CLI

```bash
postman collection run "$COL" -e "$ENV" --no-report-events \
  -r cli,json,junit,html \
  --reporter-json-structure newman \
  --reporter-json-export "$OUT/results.json" \
  --reporter-junit-export "$OUT/results.xml" \
  --reporter-html-export "$OUT/results.html"
```
- **`--reporter-json-structure newman` is required** for the summary to work. The native structure is different and the script rejects it.
- **Always `--no-report-events`**, unless the user explicitly wants to send results to Postman.
- Don't combine `--output` with `-r`: the CLI rejects it.
- Temporary mode: replace `postman` with `npx -y -p postman-cli postman`.

### Useful options (both tools)

| Need | Option |
|---|---|
| Run only one folder or case | Newman: `--folder "<name>"`. Postman CLI: `-i "<name>"` (repeatable, keeps the order). Use the exact folder name, e.g. `001.pets`. In Postman CLI, the `"folder/subfolder"` path did **not** work with these collections: use just the name |
| Override a variable | `--env-var "host=https://api.x.com"` |
| Self-signed certificates | `-k` / `--insecure` |
| Per-request timeout | `--timeout-request 10000` |
| Stop at the first error | `--bail` |
| Don't fail the process on red tests | `-x` / `--suppress-exit-code` |

**OAuth2 tokens in openapi2postman collections**: the `000.authorizations` folder obtains the token and stores it in the environment for the rest of the run. If you filter folders, include it first (Postman CLI: `-i "000.authorizations" -i "001.pets"`). Otherwise, the cases with auth go without a token.

**Exit code**: `0` if everything passes, `1` if any test or request fails (verified in both). In CI this works as a quality gate. An exit `1` is **not** a skill error: the summary must still be generated.

## Step 7: high-level summary

Run the script included in this skill on the JSON:

```bash
node <this-skill-folder>/scripts/resumen-reporte.js "$OUT/results.json"
# optional: --max-fallos 20   (by default lists up to 50 failed cases)
```

It returns, in Markdown: total passed and failed cases with success %, assertions, duration, a table per folder (resource), the **most frequent failure reasons** grouped (e.g. `8 × expected status 400, got 200`, `response does not match the schema (AJV)`, `connection error: ENOTFOUND`) and the list of failed cases with each red assertion.

Give the user:
1. Path(s) of the generated reports.
2. Totals: passed / failed / success %.
3. Main failure reasons, **interpreted**. Hints for openapi2postman collections:
   - Many `expected status 400, got 200/201`: the API does not validate input (required fields or types) as the spec declares.
   - `expected status 2xx, got 400`: review the environment's filler values or, if it was generated without `is_inline: true`, numbers and booleans sent as strings.
   - `expected status 404, got 200`: the API does not return 404 for nonexistent IDs.
   - `expected status 401/403, got 2xx`: the endpoint is not protected as the spec says, or the `not_authorized_token`/`forbidden_token` tokens are set incorrectly.
   - `response does not match the schema (AJV)`: the response does not match the contract. The AJV detail is in the JSON/HTML report.
   - `connection error`: wrong host, VPN or certificates (`-k`).
   - Almost everything fails with 401: the token is missing or the `000.authorizations` request failed.
4. Don't make up causes: if the reason is not clear, say so and point to the specific case in the report.

## Out of scope

- Generating or regenerating the collection (see the `generar-coleccion-postman` skill)
- Installing Node.js/npm
- Fixing the API or the spec based on the failures (they are only reported and interpreted)
- Running from the Postman desktop app (Collection Runner): it is manual; if the user prefers it, tell them to import collection + environment and use "Run collection"
