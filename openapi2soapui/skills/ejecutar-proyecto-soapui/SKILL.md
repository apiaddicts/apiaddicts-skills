# Run a SoapUI project via the TestRunner CLI

This skill covers **only** how to install/locate and run the SoapUI TestRunner on an already generated `.xml` project (for example with the `generar-proyecto-soapui` skill). It does not cover how to generate that project, nor installing Docker/JDK themselves — it assumes the user decides which environment they have available and this skill guides them on what to do with it.

## Step 0 — present the options, never assume one

Before running anything, present the user with the 3 options and their requirements, and ask which one applies to their environment (or whether they already have SoapUI installed and where). Don't pick one by default without confirming — each has different trade-offs.

| Option | Requires | Limitation / note |
|---|---|---|
| **1. Java + Maven jar** | JDK + Maven + network access to the SmartBear Nexus repo | Initial download of transitive dependencies (can be heavy); the version is pinned to whatever is declared (this repo uses `5.9.1`) |
| **2. Docker** | Docker installed and running | No JDK needed on the host — the JRE is inside the image. Watch out for paths on Windows/Git Bash: use absolute paths and `MSYS_NO_PATHCONV=1` if `/project` gets oddly converted |
| **3. Existing installation** | The user already has SoapUI installed (full installer) and knows/can find the path | Installs nothing new. The official installer ships its own embedded JRE — it doesn't need the system Java |

No option is "zero dependencies": SoapUI Core is a Java library, so there is always a JVM running somewhere (on the host, inside the Docker container, or embedded in the installer).

## Option 1 — Java + Maven jar

Useful if the pipeline is already Java/Maven and you don't want to install the full app.

1. Check that a JDK is available:
   ```bash
   java -version
   ```
2. Resolve the SoapUI Core jar + its dependencies. If you have a `pom.xml` at hand (for example this repo's own), add the repository and the dependency if they're not there:
   ```xml
   <repositories>
     <repository>
       <id>SmartBearPluginRepository</id>
       <url>https://rapi.tools.ops.smartbear.io/nexus/content/groups/public/</url>
     </repository>
   </repositories>
   ```
   ```xml
   <dependency>
     <groupId>com.smartbear.soapui</groupId>
     <artifactId>soapui</artifactId>
     <version>5.9.1</version>
   </dependency>
   ```
3. Download the jars into a local folder:
   ```bash
   mvn dependency:copy-dependencies -DoutputDirectory=lib
   ```
4. Run the runner, invoking the same class that `testrunner.bat` uses internally:
   ```bash
   java -Dlog4j2.formatMsgNoLookups=true -cp "lib/*" com.eviware.soapui.tools.SoapUITestCaseRunner path/to/soapui-project.xml
   ```
5. Optionally, adjust memory if needed: add `-Xms128m -Xmx1024m` before `-cp`.

If this specific repo already declares that dependency (`pom.xml`, `soapui.version` property), use the same version to avoid compatibility surprises — check it before pinning the version in the auxiliary project.

## Option 2 — Docker

SmartBear's official image for open source SoapUI: `smartbear/soapuios-testrunner` (Docker Hub). Don't confuse it with `ready-api-soapui-testrunner`, which is for ReadyAPI (the commercial product), not for open source SoapUI.

1. Check that Docker is available:
   ```bash
   docker --version
   ```
2. Run it mounting the project folder and the reports folder:
   ```bash
   docker run \
     -v "/path/to/project-folder":/project \
     -v "/path/to/reports-folder":/reports \
     -e COMMAND_LINE="/project/soapui-project.xml" \
     -it smartbear/soapuios-testrunner:latest
   ```
3. Check the container's exit code for the pipeline gate:

   | Exit code | Meaning |
   |---|---|
   | `0` | Run OK (doesn't imply all test cases passed — check the log/report anyway) |
   | `102` | Project not found in `/project` |
   | `103` | Error during the run |

## Option 3 — Locate an existing installation

The installation path is **never assumed** (e.g. don't take `C:\Program Files\...` for granted). If it hasn't been confirmed in the conversation, ask for it. If the user doesn't know it, offer them ways to find it themselves instead of scanning the whole disk:
- Start menu shortcut → right click → Properties → the "Target" field shows the executable's path
- Windows: `where.exe SoapUI.exe` (if it's on the PATH)
- Confirm that `bin\testrunner.bat` (Windows) or `bin/testrunner.sh` (Linux/Mac) exists inside that path

Run:
```powershell
& "<install-path>\bin\testrunner.bat" "path\to\soapui-project.xml"
```
or on Linux/Mac:
```bash
<install-path>/bin/testrunner.sh path/to/soapui-project.xml
```

The official installer ships its own embedded JRE (`testrunner.bat`/`.sh` first looks for `../jre/bin`, and only falls back to `JAVA_HOME`/PATH if that folder doesn't exist) — that's why this option doesn't depend on having Java installed separately.

## Note on version compatibility

The SoapUI version used to **run** doesn't need to be identical to the one the tool used to **generate** the project — the SoapUI project `.xml` format is stable across 5.x versions. If strange XML parsing errors show up when opening/running the project, then it's worth checking whether there's a major version mismatch.

## Out of scope

This skill does not cover:
- Generating the SoapUI project from an OpenAPI spec (see the `generar-proyecto-soapui` skill)
- Interpreting or parsing the results beyond the exit code and the raw testrunner logs
- Installing Docker or the JDK themselves — it assumes the user already has one of the 3 environments available, or decides to install it on their own
